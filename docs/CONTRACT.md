# Modbus WASM local contract update (2026-10-27)

Current main `c9c3d83` includes merged #32 basic Modbus, #33 register-bit reads and #44 FC22 register-bit writes. The tables below describe the guest contract and the verified simulated Hub boundary, not production deployment. tyaro/banto-industrial#881 merged with Modbus numeric/Bool read, FC3/FC4 handshake and independently gated FC5/FC16 loopback tests; tyaro/banto-industrial#884 merged with register-bit Bool adapter/Hub join tests and pre-send write refusal. These tests used pinned guest components and their actual manifest. Physical PLC, GUI and deployed runtime remain unverified. In addition to numeric FC3/FC4 reads, `3xxxx.N` / `4xxxx.N` Bool reads use decimal `N=0..15`; a holding register-bit write `4xxxx.N` is sent alone as one FC22 Mask Write Register request that changes only that bit; `3xxxx.N` writes are rejected before send. tyaro/banto-industrial#884 verified the earlier refusal of the #33 pin. tyaro/banto-industrial#896 then moved the Modbus Hub pin from #33 (`02a92645`) to #44 (`c9c3d83`) and accepted FC22 in adapter and Hub loopback tests: set/clear with exact masks through the saved Hub mode/allowlist, permission and audit gates, pre-send refusal by either the Hub or the guest gate, an item-level device exception, and a mismatched acknowledgement that fails without replay. In the author's manual check at the adapter layer, not through Hub REST or preflight, one iQ-R CPU over Modbus/TCP accepted FC22 and changed only the target bit; one PC Modbus simulator gave no response at all, so the batch timed out and the connection was dropped. The item-level exception path has not been seen on a physical device, and production write enablement still needs separate approval. The optional guest write world requires both `write_mode=enabled` and one allowlist span covering the whole request. The independent Hub saved policy, operational gate and audit were exercised in tyaro/banto-industrial#881 loopback tests; physical and production use remain unverified. Historical U16/U32-only comparison and initial Hub pin notes farther below describe their original stages.

The numeric types are `i16/u16/i32/u32/i64/u64/f32/f64`. Each tag occupies one, two or four registers. `low_high` and `high_low` are supported. An FC16 run is capped at 123 words. FC22 uses AND mask `!(1 << N)` and OR mask `1 << N` (set) or `0` (clear), and its acknowledgement must echo the address and both masks. A device without FC22 that answers with an exception yields an item-level `Device` error; a device that does not answer at all times out the batch and drops the connection. `write_mode` defaults to `disabled`, and an enabled mode requires `write_allowlist`. All items must pass type, width, value, area and span checks before a frame is sent. An uncertain response poisons that connection. No automatic address scan was performed. Apart from the author's manual adapter-layer FC22 check described above, no physical PLC write was performed. Hub integration was verified only in the pinned tyaro/banto-industrial#881 / tyaro/banto-industrial#884 / tyaro/banto-industrial#896 simulated adapter and loopback paths described above.

`item-error.verification-failed` means the read-back after a write was sent does not match the written value, so the write may have taken effect on the PLC; `item-error.rejected` is limited to refusals before anything is sent. The current guest does not return `verification-failed`; the host follows in tyaro/banto-industrial#902.

# API と WIT の照合

SLMP follow-up: the separate guest uses the current session.connection and read interfaces for a controlled 0101 -> SD -> D/u16 path. `read.plan` may return several steps; a verified contiguous D run has ordered original tag indices in `covers`, one per response word, up to the core's 960-word 0401 limit. Unknown-range tags remain individual steps; gaps are not read. `read.decode` returns one result per cover. Unsupported or verified out-of-range tags remain uncovered for the host's item-level `Unsupported` result. A whole-batch PLC refusal gives each cover an item-level `Device` error; malformed or mismatched responses remain fatal, after which the host closes the connection. A recognized Q/R wire series allows explicit reads when the configured range is unknown, at the operator's responsibility; success does not verify range. An unknown name/code or 0101 refusal does not establish Q/R 0401 framing in this guest. [The discovery snapshot proposal](SLMP_DISCOVERY_CONTRACT.md) defines CPU identity, count scope, unknown reasons, and generation invalidation without changing WIT or Hub in this stage. Compatibility of a future structured WIT interface remains to be tested.

native 比較の固定元: banto-industrial `a0d01aa2` の [API 実装](https://github.com/tyaro/banto-industrial/tree/a0d01aa2/crates/banto-driver-api) と [Modbus 実装](https://github.com/tyaro/banto-industrial/tree/a0d01aa2/crates/banto-driver-modbus)。Hub の実装状態は [PR #843](https://github.com/tyaro/banto-industrial/pull/843) の merge `4c6b126a` に照合する。Hub は既存 WIT の loader / Wasmtime runtime / `FrameConnection` アダプターを持ち、固定ゲスト SHA で FC3・単一 U16 を登録している。このリポジトリの U32 版は Hub に登録されていない。

`drivers/modbus` の要求は Hub native の FC3・単一 U16（1レジスタ）または U32（2レジスタ）要求と同じ MBAP 形である。[独立した比較試験](../comparison/src/lib.rs) は Hub `a0d01aa2` の公開 `FrameDriver` / `FrameConnection` を固定 Git 依存で実行する。U16 の共有フィクスチャ12件と U32 の15件を [Wasmtime 比較試験](../runtime-comparison/src/lib.rs) でも再利用する。U16 は10件、U32 は13件で native・コア・WASM の値と分類が一致する。各2件は**意図的な差**: native の PDU 解析は宣言データ後の余剰バイトを受理するが、コアと WASM は `Framing` で拒否する。この U32 版の Hub runtime 経由実行、文字列、複数タグ、FC1/2/4 は対象外。

U32 の各レジスタ内のバイト順は big endian。固定版 native の `decode_register_value` では `high_low` が先頭を上位16 bit、`low_high` が先頭を下位16 bit として扱う。native の `create_connection` は `word_order` 未指定時に `low_high` を使う一方、native の `settings_schema` のフォーム既定値は `high_low` である。コアとゲストの未指定時は実際の native 接続に合わせて `LowHigh`、ゲストの設定フォーム既定表示も `low_high` とする。`address.parse` は U32 開始 offset 65534（参照番号 `465535`）まで受理し、65535（`465536`）を拒否する。`address.offset` の U32 はタグ幅である2 wordずつ進み、`address.offset-words` は型と無関係に1 wordずつ進む。コアは要求生成時にも同じ末尾範囲を検査する。Hub 固定ゲストと Hub 保存値の既定値は変更しない。

## 初版境界の決定

2026-10-25 に以下の初版方針を承認済み。WIT の `world driver` は設計 §6.2 の `session` / `read` / `address` / `config` を全て export する。読み取り専用 world を使用し、縮小した独自 world や WASI import を作らない。Hub 固定ゲストは Modbus TCP の FC3・単一 U16、このリポジトリのゲストは単一 U16/U32 を扱う。書き込み、シリアル、SerialOverTcp、文字列は対象外。

1. **接続テスト**: `address` に `use types.{tag-spec}; probe: func() -> option<tag-spec>` を加える。Modbus は `40001` / `u16` を返す。Hub が `parse` してから `read.plan` → 送受信 → `read.decode` を実行し、エラーを成功扱いにしない。`none` の場合だけ handshake 完了で成功とする。Hub の既存テスト経路に合わせ、`connectionId` なし、または既存セッションなしなら直接接続する。保存済み接続が稼働中で設定 fingerprint が一致すればセッションを再利用する。設定変更済みなら別接続せず「保存してからテスト」を返す。`probe` の取得は状態を変えない検証用 export とする。
2. **設定版**: WASM manifest の `settingsVersion` は必須の正整数で、初版は `1`。欠落、`0`、整数以外は拒否する。U32 追加では表示名とプラグイン `version` を `0.2.0` に更新する。既存の任意 `word_order` 設定を使い、設定移行も WIT 変更もないため `settingsVersion=1` と `hubApi=1` を維持する。native の古い descriptor に対する欠落時 `1` の補完は変更しない。
3. **通信間隔**: v1 の `transports` は `tcp` のみ。`inter_frame_gap` はゼロとして Hub 側の既存 engine 契約に写す。シリアルと SerialOverTcp をこの契約で受理しない。時間単位と上限を伴う WIT 拡張はシリアル導入時に設計する。
4. **生値と分類**: FC3 の `u16` と `u32` は既存 WIT `types.value.uint(u64)` に拡張して返す。WASM 境界で U16 の `0..=65535`、U32 の `0..=4294967295` と型を検査し、範囲外を丸めない。`banto-driver-engine::decode_value` は変更しない。機器例外は `item-error.device`、破損フレームは `fatal-error.framing`、要求と異なる ID は `fatal-error.protocol`。`covers` の範囲・重複と結果件数は既存 `FrameSession` の検査を再利用し、独自の「全タグ必須」条件は足さない。Hub 側では U16 のみ実装済みで、U32 の境界検査は未実装である。
5. **ホスト起因の失敗**: trap、epoch 超過、メモリ上限はゲストの `fatal-error` ではない。Hub runtime の内部型で原因を保持して構造化診断に記録し、既存 API への正規化を一か所に集約する。接続用の runtime 実行失敗は `Protocol`、受信上限は現行どおり `Framing`、実通信 timeout は現行どおり `Timeout`。`FrameConnection` が `Io` / `Timeout` を返してはいけない現行規則を保つ。失敗した接続用インスタンスは破棄する。検証用の trap・実行上限は検証エラーとし、接続へ波及させない。`memory.grow` の失敗が必ず trap になるとは仮定せず、選択した runtime の実行試験で分類を確かめる。

上記の初版方針に沿う Hub loader / runtime と U16 接続テストは PR tyaro/banto-industrial#843 で実装された。U32 を Hub で利用するには、固定ゲスト SHA の更新、境界での U32 型・範囲検査、接続テスト以外の読取り経路を別作業で照合する必要がある。

独立テストホストは `settingsVersion` の欠落・`0`・負数・小数・文字列・真偽値・`u32` 超過を拒否し、`uint(u64)` の U16/U32 範囲と型を確認する。ローカル TCP の制御した応答で U16 `probe` から `read.decode` まで通す。U32 の15件は実 Wasmtime コンポーネントで照合する。これらは Hub の U32 登録・読取り適合を代替しない。

## 最小比較経路と検証の区別

1. 上記の `world driver` 全 export を持つ読み取り専用ゲストをビルドする。アドレス解析と設定検証は export として実装し、対応しないタグ型や設定は明示的に拒否する。ソケットはゲストに渡さない。
2. 既存の [native 比較試験](../comparison/src/lib.rs) の U16 12件と U32 15件を共通入力として再利用する。実コンポーネントの `read.plan` / `read.decode` を呼び、U16 10件と U32 13件の値・分類一致、各2件の余剰 PDU の意図的な厳密拒否を検査する。要求 MBAP と `uint(u64)` の範囲も比較する。
3. `wasm32-unknown-unknown` の `cargo check` はコアの型検査であり、コンポーネントの生成や実行ではない。WIT 型検査、コンポーネント生成、独立テストホストでの実行、Hub runtime 経由の実行を別々に記録する。この版の Hub U32 適合は未検証である。
