## 現行段階と完了条件

main `25b5a1b`（#48）では #32 Modbus 基本、#33 register-bit read、#34 SLMP V 周期収集除外、#35 標準 Q X / 標準 R SB・F 診断、#43 SLMP 範囲外 bit の読取り除外、#44 Modbus FC22 register-bit write、#47 WIT の `item-error.verification-failed` 追加（ゲスト未使用）がマージ済みです。Modbus は FC1/FC2 Bool、FC3/FC4 数値 8 型と register-bit Bool を読取り、任意の FC5/FC16 write-v1 と 4xxxx.N の FC22 register-bit write を既定無効のゲスト設定で制限します（FC22 は tyaro/banto-industrial#896 で模擬 Hub 受入れ済み）。SLMP は既知 Q/R の明示読取り、D/W 数値 8 型と対応 bit Bool、既定無効のゲスト書込み試作、任意の diagnostics-v1 を持ち、同じ接続の SD で exact 点数を得た bit 領域では範囲外のタグを読みません（#43 は tyaro/banto-industrial#895 で模擬 Hub 受入れ済み）。数値 8 型は `i16/u16/i32/u32/i64/u64/f32/f64`。現状と残件はローカルの引継ぎメモ `docs/STATUS.md`（git 追跡外）、個々の経緯は git 履歴と各 PR に残します。

## 対応範囲の拡張計画（2026-10-28 作者決定）

未対応項目への対応順と方針を定める。各段階は個別 PR とし、ゲストを変える PR では Hub 固定版との契約差確認、manifest の版更新、banto-industrial 側の模擬 Hub 受入れまでを 1 単位とする。読取りを書込みより先に、WIT 不変の項目を WIT・Hub 変更を要する項目より先に進める。書込みは既定無効で、ゲストの明示 allowlist と Hub の独立ゲートの両方を要する。実機確認は別途承認を受け、README・CI では模擬確認と実機確認を区別する。

作者の決定:

- FC22 非対応機器は、設定で明示して 4xxxx.N 書込みを送信前に `Rejected` とする。RMW 方式は引き続き不採用。
- SLMP のブロック切替式 R（現在ブロックをゲストから確定できない）は恒久的に対象外とする。R の代わりに ZR を案内する。SD / SW / SM 等の特殊デバイスへの書込みも当初は恒久的に対象外としたが、2026-11-05 の作者決定で取り消した。H の時計合わせで SD・SM を書く。タグとしての特殊デバイスの書込みはこの段階では開かない（下の「H の設計」）。
- 文字列、Modbus FC6 / FC15、SLMP 3E はいずれも利用予定があるため採用する。
- SLMP の ASCII コード通信（E3）は採用しない（2026-10-28 作者決定で取消し。当初の採用は文字列の意味と取り違えたもので、通信の ASCII 方式には利用予定がない）。文字列は C1 で扱う。

C0 の確認結果（2026-10-28、Hub main `1120419` の静的照合）: Hub の WASM 経路は文字列を通せない。タグ登録（`string`、1–128 words、UTF-8 / Shift_JIS）、engine の復号（最初の NUL で切り、不正な符号は項目エラー）、REST の read-now と書込み・監査、native SLMP の文字列は対応済みで、周期収集・履歴・ライブ表示は全ドライバで文字列を扱わない（設計どおり）。不足は WASM アダプタ（`crates/banto-driver-wasm`）だけで、`string` を宣言したゲストの読込み拒否、文字列アドレスの照合拒否、`bytes` 結果のバッチ全体 Fatal、Modbus・SLMP 書込みゲートの数値限定（`string-words` 未設定・`bytes` への変換なし）、Modbus の 1 要求 123 ワードと登録上限 128 ワードの差がある。tyaro/banto-industrial#914 はこの一部を記録している。作者の判断で Hub 側の修正はいったん保留し、C1 はその修正の後に行う。先に WIT・Hub 不変の D1・D2 を進める。

D1 の確認結果（2026-10-28、SLMP 参照マニュアル SH-080956ENG N の公式表）: S は 98H（Q/R、読取り専用、S 対応機種のみ）、Z は CCH（Q）/ 00CCH（R）、RD は 002CH（サブコマンド 0002/0003 のみ＝iQ-R）、いずれも 10 進。ゲストはこの 3 つを範囲 `Unknown` の単独 0401 読取りとして追加し、書込みは持たない。LZ（0062H、ダブルワード）は 0401 一括読出し・1401 一括書込み・0406/1406 ブロックで指定できず、0403 ランダム読出しのダブルワード点だけで読めるため、D1 では追加せずアドレス解析で拒否する。LZ を読むなら 0403 のフレームを新設する別段階になる（採否は未決）。

D2 の確認結果（2026-10-28、作者決定 A）: SD306–307（ZR の点数）は QnU（Q00UJ を除く）だけで、拡張 D または拡張 W を 1K 点以上設定したときだけ値が入る。拡張 D/W は CPU のシリアル先頭 5 桁 09042 以降が必要だが、SLMP ではシリアルを読めず、handshake も拡張点数を読まないため、ゲストは適用条件の証拠を得られない。そこで `q_zr`（`plan_q_zr`/`decode_q_zr_count`）は変更せずゲストからも呼ばず、Q の ZR は標準 R の ZR と同じ方式（0401 サブコマンド 0000、デバイスコード B0H、3 バイトの 16 進番号で 24 ビットに収まること、範囲 `Unknown`、1 タグ 1 要求、書込みなし）で開く。対象は標準 Q のうち Q00JCPU（標準 RAM なし＝ファイルレジスタなし、[QCPU 取扱説明書 SH-080483ENG 印刷 p.147](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080483eng/sh080483engbc.pdf#page=149)）と Q00UJCPU（「ファイルレジスタを持たない」、[QnUCPU 機能解説 SH-080807ENG 印刷 p.392](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080807eng/sh080807engae.pdf#page=394)）を除いた機種で、Q25PRH は従来どおりファイルレジスタの対応表を持たず経路なし。注意: QnU では ZR の点数を超える ZR 番号が拡張 D/W 領域を指しうる（[QnU pp.402–404](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080807eng/sh080807engae.pdf#page=404)）ため、ZR の読取りが成功しても ZR の範囲の証明にはならない（読取り専用・範囲 `Unknown` のままなので害はない）。WIT・Hub は変更なし。

2026-11-06 作者決定: ZR のアドレスは 10 進（標準 Q・標準 R とも。GX Works の表記に合わせる）。以前は 16 進だった（R は初期から、Q は D2 から）。`ZR10` は 10 番、`ZR1A` のような英字は拒否し、Q の 24 ビット上限は `ZR16777215` が送信可・`ZR16777216` が拒否。読取り専用・範囲 `Unknown`・1 タグ 1 要求・対象機種・デバイスコード B0H・番号欄（Q 3 バイト・R 4 バイト）は変えない。Hub が解析結果の `index` を ZR の番号として使う場合、既存の 16 進タグは別の番号になる。

D3 の設計（2026-10-28 作者決定: W10000H 未満に限る、診断は変えない、拡張 D は別段階）:

- 公式資料の事実。(1) 拡張 W は内部 W の直後から番号が続き（[QnU 機能解説 SH-080807ENG 4.8 節 印刷 p.402](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080807eng/sh080807engae.pdf#page=404)）、内部と拡張の間に物理的な連続性はない。プログラムのブロックデータ・インデックス修飾・オートリフレッシュは境界をまたがないよう求められている（同 p.405）。(2) SD310–311 は「内部 W と拡張 W の合計点数」の 32 ビット値（[QCPU 取扱説明書 SH-080483ENG 付録 3 印刷 p.551](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080483eng/sh080483engbc.pdf#page=553)）で、対象は QnU（Q00UJCPU を除く）。拡張 D/W 自体はシリアル先頭 5 桁 09042 以降の CPU が必要（QnU 付録 2）。(3) SLMP・MC では拡張 W も通常の W（デバイスコード B4H、16 進）として「アクセス先 CPU の番号範囲内」で指定する。W10000H 以降へのアクセスに対応しない CPU では ZR に読み替えて指定する（[SLMP 参照マニュアル SH-080956ENG N 印刷 p.38 注 *4](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080956eng/sh080956engn.pdf#page=40)、[MC 参照マニュアル SH-080008 印刷 p.69](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080008/sh080008ab.pdf#page=71)）。非対応 CPU に 65536 以上を指定すると終了コード 4030H、範囲外は 4031H で拒否される（QCPU 取扱説明書のエラーコード表）。
- 対象: 0101 で標準 Q と分類され、かつ QnU の型式コード（Q00UJCPU 0260H を除く）の CPU だけ。Q00J/Q00/Q01/QnH・Q25PRH・R は変えない。経路は E2 の固定宛先と 4E/3E のどちらでもよく、点数の取得も同じ経路で行う。
- 取得: SD302–303 の読取り（バイト列は不変）の後、対象機種だけ SD310–311 を同じ接続で 1 回だけ読む。PLC の終了コードによる拒否は拡張 W を開かないだけで、接続は続ける（既存の内部 prefix 規則のまま）。データ不足を含むフレーム不正・経路やシリアルの不一致は、既存の SD 読取りと同じく致命的エラーとして切断させる。
- 整合条件: 合計 T（SD310–311）を拡張判定に使うのは、内部 W の点数 WC が SD303 で確定（`Exact`、32768 で飽和していない）し、かつ T ≥ WC のときだけ。T < WC（古い firmware で 0 など）は `Unknown` として使わない。SD303 が飽和（`AtLeast(32768)`）のときは境界 WC が分からないので、拡張は開かず現状どおり先頭 32768 点だけを読む。高速型の SD284–285 で WC を得る案は後の候補とする。
- タグの判定（W の 1・2・4 ワードのタグ全体で判定）: 全体が WC 未満は従来どおり範囲内。全体が [WC, T) にあれば範囲内（拡張 W）として W/B4H で直接読む。WC をまたぐタグは境界越えとして未対応（`Unsupported`）。T 以上に届くタグは範囲外確定（R と同じく設定エラー）。T = WC（拡張なし）の場合は T が W の確定点数になり、WC 以上は範囲外確定になる。
- 要求の組み方: 隣接タグのまとめ読みは WC をまたがない。拡張 W として読むのは W10000H 未満に収まるタグだけ（作者決定）。W10000H 以上に届くタグは、T 未満でも CPU・中継局の対応が 0101 から分からないため未対応（`Unsupported`）とし、T 以上なら範囲外確定のまま。ZR への読み替えは行わない（ZR 点数の SD306–307 は条件付きで、拡張 D 点数も要るため、経路別の変換は持たない）。
- 書込み: D3 は読取りだけ。W の書込みゲートは従来どおり内部 W（SD303）の範囲で判定し、T を使わない。
- 診断（diagnostics-v1）: 変えない（作者決定、案 1）。Q の W は従来どおり内部の範囲で報告し、T は使わない。

F の設計（ワード内ビット書込み、2026-10-28 作者決定: 非原子性は明記して受入れ、許可はビット単位、1 要求 1 ワード、確認読みの終了コードは `VerificationFailed`）:

- 非原子性の扱い。RMW は読取りから書き戻しまでの間に PLC のプログラムや他の通信局が同じワードの他のビットを変えると、その変更を上書きする。読み直しで確かめられるのは書いたビットだけで、上書きは検出できない。native と同じくこれを受け入れ、契約と設定の説明に明記する。利用者は、PLC のプログラムも他の通信局も他のビットを書かないワードだけを allowlist に入れる前提とする。
- 対象。0101 で確定した標準 Q/R の D と W のワード内ビット（既存の読取り文法 `D100.5`・`W1A.0`、ワード番号は D が 10 進・W が 16 進、ビットは 16 進 0–F）。Q25PRH・未知機種、D/W 以外（R・ZR・SD・SW・Z 等）は従来どおり送信前に拒否する。D3000・D3001 は保護のまま。
- 範囲の根拠。対象ワード 1 点が既存のワード書込みゲートと同じ判定で範囲内に入ること（R の D/W は確定点数、Q の W は内部 W の SD303）。既存ゲートは標準 Q の D を通さない（数値書込みも同じ）ため、Q の D のビットも送信前に拒否する。Q の D を開くなら SD302 の内部 D 範囲で数値とビットをまとめて別段階で扱う。D3 の拡張 W は使わない。
- 許可の単位（作者決定: ビット単位）。ゲストの allowlist（`d_u16_write_allowlist`）と Hub の独立ゲートに、ビット区間 `D100.3-D100.5`・`W1A.0-W1B.F` を足す（ワード番号は D が 10 進・W が 16 進、ビットは 16 進 1 桁の大文字、始点と終点は同じデバイス）。区間は（ワード番号, ビット）の順で比べ、逆順は拒否、1 区間は 7168 ビット以下。書く各ビットがいずれかのビット区間に入ることを要し、ワード区間（`D100-D105`）はビット書込みを許可しない（明示した区間だけを開く）。ビット区間どうしは同じデバイス内で昇順・重複なし、ワード区間とは独立に数える。区間数の上限 16 と全体の長さ 256 文字は共通。D3000・D3001 にかかるビット区間は拒否する。既存の保存値はそのまま同じ意味を持つ。
- 1 回の書込み要求（作者決定）。`write-next` に渡る項目がすべて同じ 1 ワードのビット（重複なし、値は `Bool`）のときだけ受け付ける。各項目の書込み値でセット・クリアのマスクを作り、同じビットに対する重複・矛盾は送信前に全項目 `Rejected`。別のワードや通常の数値・ビットデバイス項目と混ざった要求は全項目 `Rejected`（Hub の既存ゲートが 1 回の要求を 1 区間に限るのと同じ扱い。分割は Hub 側の将来課題）。
- 手順。(1) 0401 ワード単位で 1 点を読む、(2) 1401 ワード単位で 1 点を書き戻す、(3) 0401 で読み直す、の 3 段を write-v1 の `send` を 3 回返して行う（WIT 不変、Hub engine の手順上限 `3 × 項目数 + 8` の範囲内）。どの段でも 4E はシリアル番号、3E は発行順で応答を照合し、経路折返しを検査する（E1・E2 と同じ）。

- SLMP: `D<n>`・`W<HEX>` の 1–128 ワード。範囲根拠は同じ幅の数値タグと同じ規則（R は exact 点数、Q の D は内部範囲を越えると明示の範囲 Unknown、Q の W は D3 の規則）で、診断も全範囲で判定する。読取りは 0401（数値と同じくまとめ読み可）で、ワードの下位バイト先、すなわち応答のデータバイトをそのまま `2 × n` バイトで返す。`word_order` は文字列に効かない。書込みは文字列 1 項目だけを 1401 1 回で書き、許可リスト・同じ接続の SD の根拠・D3000/D3001 の保護・Q25PRH の試験書込みの制限は数値の書込みと同じ。数値と同じく確認読みはしない。4E・3E・経路指定（E2）で共通。

ゲスト単体・Wasmtime 試験・CI のみで、Hub 模擬受入れ（固定の更新、文字列の component 試験、t12）と実機は未実施。

G は U/G（G1）・ラベル・他機種の順に段階を分ける（2026-10-29 作者決定）。G1 の設計（2026-10-29 作者決定: 対象はユニットのバッファメモリと RCPU の CPU バッファメモリ、読取り専用、型は数値・ワード内ビット・文字列。根拠は SLMP 参照マニュアル SH-080956ENG N 付録 1 印刷 pp.212–216）:

- 表記: `U<h>\G<n>`。`h` は先頭 I/O 番号の上位 3 桁を 16 進 1–3 桁（大小文字可、正規表記は大文字・先頭の 0 なし）、`n` はバッファメモリのアドレスを 10 進（正規表記は先頭の 0 なし）。ワード内ビットは `U<h>\G<n>.<b>`（`b` は D と同じ 16 進 1 桁）。`HG`（定周期エリア、マルチ CPU 専用）・インデックス修飾・間接指定・`J\` リンクダイレクトは扱わず parse エラー。
- 対象と経路: 標準 Q はユニットの `U0`–`UFF`、標準 R はそれに加えて CPU バッファメモリ `U3E0`–`U3E3`（マルチ CPU 1–4 号機）。Q25PRH と型式未知の機種は経路なし（ZR と同じ扱い）。
- 拒否の段階: WIT の `address.parse` は接続や型式を受け取らないので、parse では機種によらない文法と共通の上限だけを検査する。`h` が `0`–`FF`・`3E0`–`3E3` のどちらでもないもの（`U100`–`U3DF`、`U3E4` 以上）と、読む範囲の末尾が 32 ビットを越えるものは parse エラー。機種による制限（Q の `U3E0`–`U3E3`、Q で末尾が 24 ビット（16777215）を越えるもの、Q25PRH・型式未知）は handshake で型式を確定した後の `read.plan` で送信前に断り、そのタグは要求に含めず項目ごとの `Unsupported` とする（ZR などと同じ経路で、接続は切らない）。
- フレーム: 0401 のデバイス拡張指定。Q はサブコマンド 0080（デバイス修飾 `00 00`・番号 3 バイト・コード ABH・`00 00`・拡張指定 2 バイト・F8H）、R はサブコマンド 0082（番号 4 バイト・コード `AB 00`）で、拡張指定は R の CPU バッファメモリだけ FAH、ほかは F8H。拡張指定の 2 バイトは `h` の値を下位バイト先で送る。点数・応答は通常の 0401 ワード読取りと同じ。4E・3E・経路指定（E2）で共通。
- 型と読み方: 数値 8 型（`word_order` は D と同じ）、ワード内ビット（そのワードを読んでビットを切り出す）、文字列 1–128 ワード（C1 の SLMP と同じく下位バイト先・復号なし）。範囲は `Unknown` で、1 タグ 1 要求（他のタグとまとめない）。番号の上限は上の「拒否の段階」のとおり。PLC が返す終了コードは他の読取りと同じ項目エラー。`offset` は `n` を進め、`h` は変えない。
- 書込み: 持たない。U/G を宛てた書込み項目は送信前に断り、許可リストにも U/G を書けない。診断（diagnostics-v1）は範囲を持たないので変えない。
- `address.parse` の `area` はユニットごとの `U<h>\G`（例 `U3\G`・`U3E0\G`）、`index` は `n`。Hub は `area` と `index` でタグの重なりを判定するので、ユニットが違えば同じ `n` でも重ならない。
- 影響: WIT 不変。Hub の数値・ビットの読取りはゲストの文法と正規表記の往復で照合するので変更は不要の見込み。ただし Hub の WASM アダプタは SLMP の文字列タグの `area` を `D`・`W` に限っているため、U/G の文字列には Hub 側で `U<h>\G` を足す変更が要る。Hub 模擬受入れでタグ登録（`\` を含む表記）・read-now・周期収集を確認する。SLMP の manifest はこのリポジトリにない。

G1 の結果（2026-10-29）: 上の設計どおりに実装した。コアに `UnitBufferSpan` と `encode_read_unit_buffer`（要求データ長は Q が 19、R が 21 バイト）を足し、マニュアルの 2 つの通信例とバイト単位で一致することを試験した。`U` と `\G` は大文字だけを受け付け、`h` の 16 進は大小文字可、`h`・`n` の先頭の 0 は正規表記で落とす。ゲスト単体・Wasmtime 試験・CI のみで、Hub 模擬受入れと実機は未実施。

G2（他機種）の設計（2026-11-05 作者決定。資料を調べて機種群ごとに分け、G2a → G2b → G2c の順に進める。公式資料が見つからない機種は凍結する）:

- 共通の方針: 機種は今と同じく 0101 の型名と型式コードの組で判別し、表にない組は従来どおり `Unknown`（読書きしない）とする。範囲の根拠は同じ接続で読む SD の点数とし、機種群ごとに「どのフレーム・サブコマンドで送るか」「どの SD 表を使うか」「どのデバイスがないか」を持つ。WIT と Hub は変えない見込み（Hub はゲストの正規表記の往復で照合する）。書込みのゲートは機種群ごとに既存の Q か R の規則に揃える。

- G2a（Q 系・MELSEC-L。Q と同じ配線と SD 表）:
  - 対象: Q のプロセス CPU（Q02PHCPU 41H・Q06PHCPU 42H・Q12PHCPU 43H・Q25PHCPU 44H。型式コードは QnH と共有で、型名で区別する）、ユニバーサルプロセス CPU（Q04UDPVCPU 367H・Q06UDPVCPU 368H・Q13UDPVCPU 36AH・Q26UDPVCPU 36CH。コードは QnUDV と共有）、MELSEC-L（L02SCPU・L02SCPU-P 543H、L02CPU・L02CPU-P 541H、L06CPU・L06CPU-P 544H、L26CPU・L26CPU-P 545H、L26CPU-BT・L26CPU-PBT 542H）。型名・コードは [SLMP 参照マニュアル SH-080956ENG N 印刷 p.139](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080956eng/sh080956engn.pdf#page=141)。
  - 根拠: QCPU 取扱説明書の「QCPU」はプロセス CPU・冗長 CPU・ユニバーサル（QnUDPV を含む）の総称で（[SH-080483ENG 用語](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080483eng/sh080483engbc.pdf)）、点数の SD290–SD304 の CPU 欄は「QCPU・LCPU」、LCPU は L シリーズの全 CPU（[同 印刷 p.550](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080483eng/sh080483engbc.pdf#page=552)）。SLMP では L は Q と同じサブコマンド 0000/0001 を使う（SLMP 参照マニュアル 印刷 p.35）。
  - 扱い: QnPH は標準 Q（非 U）、QnUDPV は QnUDV と同じ QnU（D2・D3 の QnU 規則と SD282–285 の高速 D/W を含む）、L は標準 Q の基本の SD 表（SD290–SD304）だけを使い、QnU 向けの拡張（D2 の ZR 方針、D3 の SD310–311）は L に当てはまるかを確かめるまで使わない。Q12PRHCPU（4BH）は Q25PRH と同じ配線だけの扱いに加える。（2026-11-06 作者決定: QnUDPV は QnUDV と同じ扱いで SD282–285 を含む。L の ZR 制限はこの決定で置き換え、L は標準 Q と同じ扱いにする。Q12PRH は書込みも含めて Q25PRH と完全に同等。）
  - 残る確認: L の内蔵 Ethernet が 4E を受けるか（受けなければ `frame=3e` を案内する）。実機。

G2a の結果（2026-11-05）: 上の設計どおりに実装した。0101 の判別に QnPH 4 組・QnUDPV 4 組・L 10 組を足してどれも `StandardQ`、Q12PRHCPU/004BH を `Q25PrhWireOnly` に加えた（名前とコードの組が一致しないものは従来どおり `Unknown`）。QnPH は標準 Q（非 U）、QnUDPV は QnU（D2 の ZR 方針、D3 の SD310–311 を含む）。L は標準 Q と同じ扱いで、ZR を読み、SD310–311 は QnU の型名だけ（コード判定）なので L には当てはまらず、U0–UFF と Q の書込みの規則も標準 Q と同じ。Q12PRH は読取りが SD302/303 の内部 D/W だけで、書込みも Q25PRH と同じ扱い（SD302 で確かめた D の許可リスト書込みと、D3010–D3013 の試験書込みの設定 `q25prh_d3010_3013_test_write` を両方の組に共通で使う）。QnUDPV は QnUDV と同じ扱い（SD282–285 の高速 D/W を含む。2026-11-06 作者決定）。ゲスト単体・Wasmtime 試験・CI のみで、Hub 模擬受入れと実機は未実施。（2026-11-06 作者決定: L は標準 Q と同じ扱いで ZR を読む。Q12PRH は書込みも Q25PRH と同じ扱い）

- G2b（iQ-R 系の特殊 CPU・MX-R。R と同じ配線と SD 表、S の有無だけ違う）:
  - 対象: プロセス CPU（R08PCPU 4841H〜R120PCPU 4844H）、SIL2 プロセス CPU（R08PSFCPU 4851H〜R120PSFCPU 4854H）、安全 CPU（R08SFCPU 4891H〜R120SFCPU 4894H）、MX-R（MXR300-16 48E9H・MXR300-32 48EAH・MXR300-64 48EBH・MXR500-128 48EEH・MXR500-256 48EFH）。
  - 根拠: 点数の SD260–SD309 は標準 R と同じ番号・意味で、S（SD276/277）だけが違う。プロセス CPU は S を持つ（[iQ-R プロセス CPU ユーザーズマニュアル SH-082493ENG F 印刷 p.694](https://www.mitsubishielectric.com/dl/fa/document/manual/plc/sh082493eng/sh082493engf.pdf#page=696)）。SIL2 プロセス CPU は S を持たない（[SH-082503ENG B 印刷 p.506](https://www.mitsubishielectric.com/dl/fa/document/manual/plc/sh082503eng/sh082503engb.pdf#page=508)）。安全 CPU は SD250・SD260–SD309 が全 CPU 共通で S は Rn・RnP だけ（[iQ-R CPU ユニット ユーザーズマニュアル（応用編）SH-081264ENG AR 印刷 pp.982–983](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh081264eng/sh081264engar.pdf#page=984)。安全 CPU 専用のマニュアルは未発行）。MX-R は S を持たない（[MX-R ユーザーズマニュアル SH-082641ENG D 付録 7 印刷 p.2149](https://www.mitsubishielectric.com/dl/fa/document/manual/mxc/sh082641eng/sh082641engd.pdf#page=2151)）。
  - 扱い: 標準 R と同じ規則で読書きする。S を持たない機種群（SIL2・安全・MX-R）は S のタグを送る前に `Unsupported` とする。安全デバイス（SA\D など）は SLMP で指定できない（SLMP 参照マニュアル 印刷 pp.36–37・p.78）ので、文法にも足さない。SAFETY MODE の安全デバイスの書込み禁止と、安全 CPU（ファームウェア 32 以降）の外部からの書込み禁止範囲は PLC が終了コードで断るので、ゲストは既存の書込みと同じく `device` で返す。MX-R の Ethernet ポートはバイナリだけで、今のゲストもバイナリだけなので差はない。0101 の `MX-R`/037EH（接続局が iQ-R・MX 以外のときの代わりの応答）は `RCPU`/0360H と同じく `Unknown`。冗長構成（R6RFM）は自局の固定宛先だけを扱い、系切替の間の書込みが失われうることを設定の説明に書く（[SH-082493ENG F 印刷 p.443](https://www.mitsubishielectric.com/dl/fa/document/manual/plc/sh082493eng/sh082493engf.pdf#page=445)）。
  - 残る確認: 各機種群の実機（特に MX-R の大きい既定点数で SD が正しく読めること）。

G2b の結果（2026-11-06）: 上の設計どおりに実装した。0101 の判別にプロセス CPU 4 組・SIL2 プロセス CPU 4 組・安全 CPU 4 組・MX-R 5 組を足してどれも `StandardR`（名前とコードの組が一致しないものは従来どおり `Unknown`。`MX-R`/037EH と `RCPU`/0360H も `Unknown` のまま）。配線・SD260–SD309 の表・読書きの規則は標準 R と同じで、新しい `ModelFamily` は足していない。S だけが違い、SIL2・安全・MX-R の名前とコードの組（`r_lacks_step_relay`）では `read.plan` が S のタグを項目ごとの `Unsupported` にする（プロセス CPU は標準 R と同じく S を読む。書込みの許可は D/W/M/Y/L/B だけなので S の書込み経路はなく、診断も S を報告しないので変更はない）。冗長構成（R6RFM）は自局の固定宛先だけを扱い、系切替中の書込みが失われうることを SLMP の README に書いた。ゲスト単体・Wasmtime 試験・CI のみで、Hub 模擬受入れと実機は未実施。

- G2c（FX5。配線・SD 表・デバイスが違う新しい機種群）:
  - 根拠はすべて [FX5 ユーザーズマニュアル（SLMP 編）JY997D56001 K](https://dl.mitsubishielectric.com/dl/fa/document/manual/plcf/jy997d56001/jy997d56001k.pdf) と [FX5 ユーザーズマニュアル（応用編）JY997D55401 AH](https://dl.mitsubishielectric.com/dl/fa/document/manual/plcf/jy997d55401/jy997d55401ah.pdf)。
  - 対象: FX5U・FX5UC・FX5UJ・FX5S の CPU（0101 の型式コード 4A21H〜4B5FH の表、SLMP 編 印刷 pp.109–110）。型名の文字列はマニュアルに例がないので、コードの表と型名の先頭 `FX5` の両方で判別する（作者決定）。実機で型名を記録する。
  - フレーム: 3E と 1E だけで 4E はない（SLMP 編 印刷 p.8）。ゲストは FX5 では `frame=3e` を要する。4E のまま繋ぐと 0101 に応答がなく型式を確定できないので、設定の説明で 3E を案内する。宛先は自局だけ（ネットワーク 00H・局 FFH・I/O 03FFH、印刷 pp.23–24）。監視タイマは CPU には 0000H（無限待ち）を指定するよう書かれている（印刷 p.27）ので、FX5 では 0000H を送る（作者決定。他の機種は今の 0010H のまま）。応答待ちの打切りは Hub の時間切れが受け持つ。
  - サブコマンドとデバイス: 0401/1401 は Q と同じ 0000/0001（デバイスコード 1 バイト・番号 3 バイト）。0002/0003 はない。1 回の上限は Q と同じ 960 ワード・3584 ビット（印刷 pp.57–60）。デバイスは X・Y・M・L・F・B・S・D・W・SB・SW・SM・SD・Z・R（ファイルレジスタ、AFH、10 進）・T/ST/C 系・LC 系・LZ・G がある。V・LT・LST・ZR はない（印刷 pp.66–67）。LCN・LZ は 0401 で読めない。
  - X・Y の番号: FX5 の X・Y は 8 進で書くが、バイナリでの番号の送り方がマニュアル内で食い違う（「バイナリは 16 進」とある一方、通信例では X20 を 20H で送っている）。実機で確かめるまで FX5 の X・Y は扱わない。
  - 点数の根拠: SD260 以降に 32 ビットで点数を持つ（X SD260/261、Y 262/263、M 264/265、B 266/267、SB 268/269、F 270/271、L 274/275、D 280/281、W 282/283、SW 284/285、T 288/289、ST 290/291、C 292/293、LC 298/299、Z 300、LZ 302、R 304/305。応用編 付録 2 印刷 pp.870–871）。番号は iQ-R に近いが同じではない（SD304/305 が R）ので、FX5 専用の SD 表を持つ。S は 4096 点固定で SD がない。
  - 書込み: 標準 R と同じく、同じ接続の SD で確定した範囲と許可リストを要する。R（ファイルレジスタ）の書込みは開かない（作者決定。読取りだけ）。
  - 対象外: MX-F（FX5 系の MX コントローラ）は 0101 の表にも見つからないので凍結。

G2c の結果（2026-11-06）: 上の設計どおりに実装した。新しい `ModelFamily::Fx5` を足し、0101 の型式コードが FX5 の表（48 組）にあり、型名が `FX5` で始まるときだけ FX5 とする（表のコードで型名が違うもの、`FX5` の型名で表にないコードは従来どおり `Unknown`）。配線は Q と同じ（0401/1401 のサブコマンド 0000/0001、番号 3 バイト、1 回 960 ワード・3584 ビット）。FX5 は 3E・自局だけで扱い、4E や他局・マルチ CPU の宛先で FX5 と判別したときは型式未知と同じく SD も読まず、読取りは計画せず、書込みは送る前に断る（`frame` の設定の説明に、FX5 は 3E が要り 4E では 0101 に応答しないことを書いた）。FX5 と判別した後は、その接続のすべての要求（SD・読取り・書込み・RMW・診断）で監視タイマ 0000H を送る。範囲は FX5 専用の SD 表（`fx5_sd`、`BasicArea::R` を追加）で、SD280–283（D・W）を 1 回で読んだ後に SD304–305（R）を別の要求で読み、M/L/B の許可や診断があれば SD262–275 を読む（R と同じ配置。Y の点数は使わない）。SD を断られた点数は既存の機種と同じく `Unknown`。読取りは標準 R と同じ扱いで、M・L・F・B・S（範囲 `Unknown`・読取り専用）・D・W（word-bit・文字列を含む）・SB・SW・SM・SD・Z（読取り専用）・T/ST/C 系・LCS/LCC を読む。ファイルレジスタ `R<n>`（AFH、10 進、ワード）を文法に足し、FX5 だけで読取り専用（範囲は SD304–305。範囲内で隣り合うものは D と同じくまとめる）、Q・R の機種群では `read.plan` で項目ごとの `Unsupported` にした。FX5 の X・Y・V・LT/LST 系・ZR・RD・LCN・`U\G` は `Unsupported`。書込みは標準 R と同じ規則（`write_mode=enabled`・許可リスト・同じ接続の SD の範囲）で D/W の数値・文字列・word-bit と M/L/B だけを Q の配線で送り、X・Y・R は書かない。診断は機種群 `fx5`、D/W/M/L/B/SB/F と R（SD304–305）の点数を報告し（X・Y は報告しない）、4E・他局で使えない FX5 は `fx5-requires-3e-own-station` とする。WIT・Hub は不変。ゲスト単体・Wasmtime 試験・CI のみで、Hub 模擬受入れと実機は未実施。残件: 0101 は型式が分かる前なので 0010H のまま送る（FX5 が 0010H の 0101 に応答することを実機で確かめる）。FX5 の X・Y と `U\G` は実機で確かめるまで未対応のまま。FX5 の型名の文字列を実機で記録する。SD262–275 の 1 回の読取りは FX5 で使わない SD272–273 を含む（実機で断られないことを確かめる）。

G3（ラベル）の設計（2026-11-06 作者決定。Hub との IF を実装より先に決める。書込みも持たせる。それ以外は推奨案どおり。根拠は SLMP 参照マニュアル SH-080956ENG N 5.3 ラベル、[印刷 pp.78–120](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080956eng/sh080956engn.pdf#page=80)）:

- 前提（マニュアル）: 扱えるのは GX Works3 のグローバルラベルで、GX Works3 の「外部機器からのアクセス」を有効にしたものだけ（既定は無効）。GX Works2 のグローバルラベル、ローカルラベル、ユニットラベル、安全 CPU の安全ラベルは扱えない（印刷 p.78）。ラベル名はバイナリでは UTF-16 で送る。1 要求の送信データは 1920 バイトまで。ラベルのビット指定（`AAA.3`）・桁指定（`K4AAA`）・変数による添字（`BBB[XXX]`、MX コントローラの 041C/141B を除く）・構造体の末端でないメンバは指定できない（印刷 p.83）。応答はラベルごとにデータ型 ID（1 ビット、2 ワード［符号なし］、3 ダブルワード［符号なし］、4 ワード［符号付き］、5 ダブルワード［符号付き］、6 単精度実数、7 倍精度実数、8 時間、9 文字列、10 文字列［Unicode］。タイマ・カウンタの接点・コイルは 1、現在値は 2 か 3）とデータ長を持つ（印刷 p.84）。64 ビット整数の型はない。
- WIT: 変えない。既存の `address`・`read`・`write-v1` で足りる。
- 表記: `@` に続けてラベル名（例 `@Tank1.Level`・`@Arr[3]`・`@M[1,2]`・`@St.Arr[2]`）。デバイスの文法とは `@` で分かれる。ラベル名の部分はゲストが文字の種類を厳密には検査せず、空・空白・制御文字・`@` の後に何もない・UTF-16 にして長すぎる（1 ラベルで 1 要求に収まらない）ものを parse エラーにする。添字は 10 進で、正規表記は空白なし・先頭の 0 なし。大小文字は書かれたとおりに送り、正規表記でも変えない（GX Works3 が大小文字を区別するかは実機で確かめる）。
- 型: bool（データ型 ID 1）・u16（2）・u32（3）・i16（4）・i32（5）・f32（6）・f64（7）・文字列（9）。i64・u64 は対応するラベルの型がないので parse エラー。時間（8）・Unicode 文字列（10）はこの段階では扱わない。ワード内ビット（`@X.3` のような表記）は SLMP が受けないので扱わない（`.` の後が数字で始まるものは parse エラー）。
- `address.parse` の戻り値: `area` は `@`（1 つだけ）、`index` は持たない（`none`）。構造体とそのメンバのように同じ記憶域を別の名前で指す関係は Hub から判定できないので、Hub は重なりを判定しない。Hub の保存の層はアドレスの重複を断らない（デバイスのタグと同じ。tyaro/banto-industrial の ui-design §3.6）ので、同じラベルを 2 つのタグに登録できる。同じラベルを 1 回の書込みに 2 度含む要求は、ゲストと Hub のゲートの両方が全体を何も送らずに断る（2026-11-06 作者決定。Hub の G3 模擬受入れ tyaro/banto-industrial#1063 で、当初の「正規表記の重複は Hub の登録で弾く」が実際の Hub と違うと分かったため直した）。`word-count` は型から決める（bool 1、16 ビット 1、32 ビット 2、f64 4、文字列は `string-words`）。`writable-area` は真（書けるかどうかは許可リストで決める）。
- `address.offset`: 最後の添字だけを進める（`@Arr[3]` に +2 で `@Arr[5]`、`@M[1,2]` に +1 で `@M[1,3]`）。添字のないラベルと、添字が負になるものはエラー。
- 機種: GX Works3 の CPU（0101 で標準 R と確定した接続）だけで送る。G2b の R 系特殊 CPU・G2c の FX5 は、それぞれの段階で入れるかを決める。標準 Q・L・Q25PRH/Q12PRH・型式未知は `read.plan` で項目ごとの `Unsupported`、書込みは送る前に `unsupported`。G1 と同じく、機種による拒否は parse ではなく `read.plan`／書込みで行う。E2 の他局経路でも同じフレームで送れるが、範囲の根拠を要しないので経路による違いはない。
- 読取り: 041C（ラベルランダム読出し、サブコマンド 0000、略号定義は使わない）で複数のラベルを 1 要求にまとめる。送信データ 1920 バイトに収まるように分ける。ラベル以外のタグとは同じ要求にしない。応答のラベルごとのデータ型 ID とデータ長をタグの型と照合し、違えばその項目だけ `rejected`（例「ラベルの型は ID 5、タグは u16」）。型は厳密に一致させる（ID 4 のラベルを u16 では読まない）。文字列はデータ長が `2 × string-words` バイトであることを要する。PLC が要求全体を断った終了コードは、そのフレームの全項目の `device`。応答の形の不正は致命的エラー。
- 書込み（作者決定で持たせる）: 141B（ラベルランダム書込み、サブコマンド 0000）。既存の書込みと同じく、ゲストの `write_mode=enabled` と許可リスト、Hub の独立ゲートの両方を要する。
  - 許可リスト: ゲストに新しい設定 `label_write_allowlist` を足す（D/W の `d_u16_write_allowlist` とは分ける。ラベル名は長く、既存の 256 文字の上限を食うため）。項目はラベルの正規表記そのもの（`@Tank1.Level`）か、最後の添字の区間（`@Arr[0-9]`、`@M[1,0-15]`。始点 ≤ 終点）。前方一致や `*` は持たない。項目の区切りと上限（案: 32 項目・2048 文字）は実装の PR で決め、Hub のゲートも同じ文法にする。既存の設定は変わらないので `settingsVersion` は上げない見込み。
  - 手順: (1) 041C で書く全ラベルを読み、データ型 ID とデータ長がタグの型と一致することを確かめる。一致しない項目が 1 つでもあれば、要求全体を `rejected` で終え、何も書かない。(2) 141B で全項目を 1 要求で書く（1920 バイトに収まらない要求は送る前に `rejected`）。(3) 確認は応答の終了コードだけで、読み戻しはしない（数値の書込みと同じ）。(1) と (2) の間にプログラムの書込みでラベルの型が変わる場合は検出できない（受け入れる）。
  - 応答の照合は既存の書込みと同じ（4E のシリアル番号、3E の発行順、経路の折返し）。(1) の終了コードは全項目の `device` で書かない。(2) の終了コードは全項目の `device`。(2) を送った後の応答の不正は致命的エラーで、再接続まで書込みを断る（既存の規則）。
  - 値: bool は 1 点のビット、数値はラベルの型の幅、文字列は Hub が渡す `2 × string-words` バイト（C1 と同じ下位バイト先）。
- 診断（diagnostics-v1）: ラベルのタグは範囲を持たないので `unknown("label")` を返す。ラベルの有無や型を診断で読みに行くことはこの段階ではしない。
- Hub の変更（banto-industrial 側、別 Issue・別 PR）: 文字列タグの `area` に `@` を足す。書込みゲートと保存済みポリシーに `label_write_allowlist` と同じ文法のラベルの許可を足す（D/W の許可リストとは別の項目）。非 ASCII のラベル名がタグ登録・REST・UI・設定パッケージ・監査を通ること、重なりの判定が `index` なしを「判定しない」と扱うことを確かめる。
- 試験（案）: parse（非 ASCII、配列 1–3 次元、構造体、`.3` の拒否、i64/u64 の拒否、長すぎる名前）、offset、041C/141B のバイト列（UTF-16、4E/3E・E2）、1920 バイトでの分割、データ型 ID とデータ長の照合（読取りの項目別 `rejected`、書込みの全体 `rejected` で何も書かないこと）、各段の終了コード、許可リスト（正規表記・添字の区間・区間外・`write_mode=disabled`）、標準 Q・未知機種で送らないこと。ゲスト単体と Wasmtime フィクスチャ。Hub 模擬受入れは別に記録する。

G3 の結果（2026-11-06、ゲストのみ。Hub 模擬受入れは別 PR）: 上の設計どおりに実装した。コアに 041C/141B のフレーム（`drivers/slmp/src/label.rs`）、ゲストに表記・許可リスト・読書き（`slmp-component/src/label.rs`）を足した。WIT と `settingsVersion` は変えていない。実装の PR で決めたこと（作者確認待ち）:

1. 機種: 0101 で `StandardR` と確定した接続だけに送る。G2b のプロセス・SIL2・安全 CPU と MX-R も `StandardR` なので送る。根拠は SLMP 参照マニュアル 5.1 の「コマンドごとのアクセス先」の表（[印刷 p.34](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080956eng/sh080956engn.pdf#page=36)）で、041A/141A/041C/141B は MX コントローラと iQ-R・iQ-L が可、Q・L は不可。FX5 は SLMP 編にラベルのコマンドがないので送らない。標準 Q・Q25PRH/Q12PRH・FX5 の読取りは項目ごとの `Unsupported`、書込みは送る前に `unsupported`。型式未知の接続は、デバイスのタグと同じく範囲のない状態の既存の扱いのまま（`read.plan` が要求全体を断る）。
2. 許可リスト `label_write_allowlist`: 項目の区切りは `;`（`@M[1,0-15]` がカンマを含むため）。空白・制御文字・`*`・空の項目・同じ項目の重複は設定エラー。上限は 32 項目・2048 文字。照合は大小文字を区別する。書込みモードは既存の `d_u16_write_mode` を共用し、`enabled` には D/W かラベルのどちらかの許可リストが空でないことを要する（従来は D/W の許可リストが必須）。
3. 1920 バイトの数え方: マニュアルはどの部分を数えるかを書いていないので、厳しい読み方（ヘッダの要求データ長、監視タイマから末尾まで）にした。名前の長さは UTF-16 の単位数（サロゲート対は 2）。
4. 文字列: マニュアルではラベルの文字列のデータ長は「定義文字数 + N」（奇数なら N=1、偶数なら 2）で、書込みは NULL 終端を含める（印刷 pp.108、115）。ゲストは読書きとも長さが `2 × string-words` であることを要し、書込みは値に 0x00 が 1 バイトもなければ送る前に `rejected` にする。定義文字数 k のラベルには `string-words = (k + N) / 2` を設定する。
5. その他: ラベルのデータは PLC の並び（下位ワード先）のままで、`word_order` は使わない。bit は 2 バイトで b0 が値、0・1 以外は致命的エラー。1 回の書込みで同じラベルを 2 度指定したら全体を `rejected`。`address.offset-words` は型を受け取らないのでラベルではエラー。041C の応答の上限は 1 ラベルにつき 4 + max(期待長, 512) バイト（GX Works3 の文字列は 255 文字までと見て、型違いのラベルが応答長の超過ではなく項目ごとの `rejected` になるように。上限は実機で確かめる）。

H の設計（2026-11-05 作者決定。役割分担、特殊デバイスの扱い、時刻の元、定期実行、順番は作者決定。iQ-R の手順はオーナー提供のマニュアル抜粋による。残る確認は末尾の「H の残件」）:

- 背景: SLMP には PLC の時計を読み書きするコマンドがない（[SLMP 参照マニュアル SH-080956ENG N](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080956eng/sh080956engn.pdf) のコマンド一覧で確認。1826 Change File Date は CPU 内のファイルの日付で、時計ではない）。三菱の CPU の時計は特殊デバイス SM・SD で合わせる。SLMP では SM（91H／R は 0091H、10 進）と SD（A9H／R は 00A9H、10 進）を 1401 で書ける（[SLMP 参照マニュアル 印刷 p.36](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080956eng/sh080956engn.pdf#page=38)）。
- iQ-R の事実（MELSEC iQ-R CPU ユニット ユーザーズマニュアル（応用編）4.1 時刻設定、印刷 pp.118–119。オーナー提供の抜粋）: 時計データは年（西暦 4 桁、1980–2079）・月（1–12）・日（1–31、閏年は自動判別）・時（0–23）・分・秒（0–59）・曜日（0＝日曜〜6＝土曜）。SM210（時計データセット要求）が OFF→ON になった後、SD210–SD216 の値を CPU に書き込み、書込みが終わると SM210 が ON→OFF になる。SD210–SD216 が有効範囲外なら SM211（時計データセットエラー）が ON になり、書き込まれない。SM213（時計データ読出し要求）を ON にすると時計データを SD210–SD216 に読み出す。範囲内でも暦にない日付（2 月 30 日）はエラーにならずに書かれ、時計機能が正常に動かない（13 月 32 日は SM211 が ON）。一部を直す場合でもすべてのデータを書く。変更するとミリ秒を 0 にし、最大 1 秒繰り上がることがある。変更のたびにイベント履歴に「時計設定」（イベントコード 24000）が残る。CPU 自身が SNTP サーバから合わせる機能もある（Ethernet ユーザーズマニュアル（応用編））。SD 一覧（オーナー提供の抜粋）では、SD210 年（西暦 4 桁）・SD211 月・SD212 日・SD213 時・SD214 分・SD215 秒・SD216 曜日（0＝日〜6＝土）をそれぞれ 1 ワードの BIN で持ち、セット側は S/U（要求時）、対象 CPU は ALL。
- Q の事実（[QCPU 取扱説明書 SH-080483ENG 印刷 p.482（SM210・SM211）・p.545（SD210–SD213）](https://dl.mitsubishielectric.com/dl/fa/document/manual/plc/sh080483eng/sh080483engbc.pdf#page=547)）: SD210–SD213 に BCD で置く（SD210 年下 2 桁・月、SD211 日・時、SD212 分・秒、SD213 年上 2 桁・曜日）。SM210 を ON にしたスキャンの END の後に時計へ書かれ、値が正しくなければ SM211 が ON。SM210 が自動で OFF に戻るとは書かれていない。
- 役割の分け方（作者決定）: ゲストは接続先ごとの手順を持つ。どのデバイスにどの形式で書くか、機種ごとの違い、完了と失敗の見分け方。Hub は接続先によらない部分を持つ。時刻の元、実行の契機、許可、監査、結果の表示。ゲストは時計も待つ手段も持たないので、時刻と実行の契機は Hub から渡す。Hub がタグ書込みで SD・SM を書く案は、三菱の知識を Hub に入れるので採らない。
- 特殊デバイス（作者決定）: 上の「作者の決定」にあった、SD・SW・SM 等の特殊デバイスへの書込みを恒久的に対象外とする決定を取り消す。H は `clock-v1` の中でゲストが組む決まった手順として SM・SD を書く。タグとしての特殊デバイスの書込み（許可リストへの SD・SM の追加）は、この段階では開かない。必要になれば別の段階として設計する。
- 時刻の元（作者決定）: Hub の PC の時計を、その PC のタイムゾーンの現地時刻に直して渡す。夏時間は考えない（PC の現地時刻をそのまま使う）。PC の時計を NTP で合わせるのは運用の前提とする。精度は秒で、送る間の遅れ（1 秒未満の見込み）と、上のミリ秒の繰り上がりは許容する。
- 実行の契機（作者決定）: 定期実行。既定は毎時 5 分のように、接続ごとに時刻表で決める。ずれを読んで比べることはせず、毎回合わせる。手動で今すぐ合わせる操作を足すかは Hub 側の設計で決める。毎回イベント履歴に 24000 が残るので、間隔は短くしすぎないよう設定の説明に書く。
- WIT: `write-v1`・`diagnostics-v1` と同じく、持つゲストだけが export する任意の interface を足す。既存の world は変えない。

  ```wit

    use types.{item-error, fatal-error};
    use session.{connection, step};

    // Hub が決めた現地の暦の日時。曜日はゲストが日付から計算する。
    record civil-time { year: u16, month: u8, day: u8, hour: u8, minute: u8, second: u8 }
    variant clock-progress { send(step), done(result<_, item-error>) }

    // 応答なしで呼んで始め、send が返ったら応答を渡して続ける。
    // send を途中で捨てるときは接続を閉じる（diagnose-next と同じ）。
    set-clock-next: func(conn: borrow<connection>, time: civil-time, prev-response: option<list<u8>>)
      -> result<clock-progress, fatal-error>;
  }
  ```

  world（ゲストが export する interface の組）は、今の `driver-with-write-and-diagnostics-v1` に `clock-v1` を足した全部入りの world を 1 つ足す案とする（組合せごとに足すと world の数が倍々に増えるため）。Hub は読み込んだゲストが `clock-v1` を持つかで時計合わせを出すかどうかを決める。対応しない機種・未知の機種は、送る前に `done(err(unsupported))` を返す。Modbus には標準の時計合わせがないので、Modbus ゲストは export しない。
- ゲストの手順（iQ-R）: 0101 で標準 R と確定した接続だけ。暦にない日付は SM211 で検出されないので、送る前にゲストが日付を検査し、範囲外（年 1980–2079 の外を含む）は `rejected` で何も送らない。
  1. SM210・SM211 を読む。SM210 が ON なら前の要求が残っているので、書かずに `rejected` で終える（OFF→ON の変化がないと書かれないため）。
  2. 1401 ワード単位で SD210–SD216 の 7 ワードを書く（年・月・日・時・分・秒・曜日の順に BIN、曜日はゲストが計算）。
  3. 1401 ビット単位で SM210 を ON にする。
  4. SM210・SM211 を読む。SM210 が OFF で SM211 が OFF なら成功。SM211 が ON なら `device`（範囲外で書かれなかった）。SM210 が ON のままなら読み直す。上限回数（案 3 回）を超えたら `verification-failed`（書かれたかどうか分からない）。ゲストは待てないので、読み直しの間隔は SLMP の往復時間にまかせる。

  各段の応答は既存の書込みと同じく照合する（4E はシリアル番号、3E は発行順、経路の折返し）。どの段でも PLC の終了コードは `device` で、以降は送らない。応答の不正は致命的エラーとして接続を切らせる。(2) の後に途中で終わっても、SM210 を ON にしていなければ時計は変わらない（SD210–SD216 の中身は書き換わる）。
- ゲストの手順（Q）: 0101 で標準 Q と確定した接続だけ。SD210–SD213 に BCD で書き、SM210 を ON にする。SM210 が自動で OFF に戻らない場合、次の回で (1) が「前の要求が残っている」と判定してしまうので、ゲストが OFF に戻す段が要るかを実機で確かめてから手順を決める。それまで Q は `unsupported` とする。
- 対象外: Q25PRH（冗長系）、型式未知の機種。E2 の他局経路は同じ 1401 で書けるが、まずは自局だけに絞る。
- Hub の役割（banto-industrial 側、別 PR）: 接続ごとの設定で既定は無効。明示して有効にした接続だけ、時刻表に従って実行する。各回を監査ログに残す（いつ・どの接続に・渡した時刻・結果）。実行は既存の書込みと同じく接続上で逐次に行い、読取りと混ぜない。
- 危険と利用者の責任（契約と設定の説明に書く）: PLC 自身の SNTP、PLC のプログラム、他の機器（GOT の時刻同期など）が同じ時計を合わせていると、互いに上書きする。PLC のプログラムが SD210 以降を直接読んでいると、書いた値が一時的に見える。時計が飛ぶと、PLC 側の時刻付きのログ・スケジュールに影響する。
- 試験（案）: ゲスト単体と Wasmtime フィクスチャで、日付の検査（閏年、2 月 29 日・30 日、月末、1979 年・2080 年）、曜日の計算、BCD（Q）、各段のバイト列（4E/3E）、各段の終了コード、SM210 が残っている場合、SM211 が ON の場合、読み直しの上限、短い応答・経路の不一致、対象外の機種で何も送らないこと。Hub 模擬受入れは別に記録する。実機確認は別途承認を得る。
- 影響: WIT に interface と world を足す。既存の interface の型は変えないので、#47（`types` の variant を変えた）と違い、古い WIT で作ったゲストもそのまま Hub に読み込める見込み。Hub の固定回帰で確かめる。Hub は world の判別、設定、時刻表による実行、監査を足す。SLMP の manifest はこのリポジトリにない。
- 順番（作者決定）: G のラベル・他機種を先に行い、H はその後にする。

H の Hub との IF（2026-11-06 作者決定。推奨案どおり）:

- world: ゲストは全部入りの world `driver-with-write-diagnostics-and-clock-v1`（session・read・address・config・write-v1・diagnostics-v1・clock-v1）を 1 つ足して使う。Hub は session と clock-v1 だけの小さい world `driver-with-clock-v1` で bind し、`banto:driver/clock-v1@1.0.0` の export があるか（`get_export_index`）で時計合わせを出すかどうかを決める（diagnostics-v1 と同じ方式）。H の残件 4 はこれで閉じる。
- 二重のゲート: ゲストの設定 `clock_set`（`disabled` 既定／`enabled`）が無効なら、送る前に `done(err(rejected))`。Hub は接続ごとの設定 `clockSync.enabled`（既定は無効）と時刻表を持つ。時計合わせは PLC に書くので、Hub は署名付きで書込みを明示的に選んだ loader で読み込んだゲストだけに出す。
- 時刻表: 接続ごとに「毎時 m 分」か「毎日 hh:mm」の 2 つの形だけ（cron 式は持たない）。時刻は Hub の PC の現地時刻。過ぎた回を後から実行して追いつくことはしない。
- 時刻の渡し方: Hub は実行の直前に PC の現地時刻を `civil-time` にして `set-clock-next` の最初の呼出しに渡す。曜日はゲストが計算する。
- 実行: broker の同じ接続で、読取り・書込みと排他にして逐次に行う。Hub はステップ数の上限（案 8）と時間切れを持ち、超えたら「結果不明」として記録して接続を閉じる。自動では再送しない（次の回は時刻表どおり）。
- 手動実行: REST `POST /api/plc-connections/{id}/clock-sync`。editor の認可と監査を通す。
- 結果: 監査ログに、いつ・どの接続に・渡した時刻・結果（成功、`unsupported`、`rejected`、`device`（終了コード）、`verification-failed`、結果不明）を残す。直近の結果は `GET` で返し、メモリだけに持つ（診断と同じ）。MCP は設定と直近の結果を見るだけで、実行は出さない。
- Hub 側の作業は banto-industrial の Issue で追う（実装はゲストの H の実装の後）。

H の結果（2026-11-06、ゲストのみ。Hub 模擬受入れは別 PR）: 上の設計と「H の Hub との IF」どおりに実装した。WIT に `wit/clock-v1.wit`（interface `clock-v1` と world `driver-with-write-diagnostics-and-clock-v1`・`driver-with-clock-v1`）を足し、既存の interface と world は変えていない。SLMP ゲストは全部入りの world で生成し、古い 4 つの world と新しい 2 つの world のすべてを満たす（CI の `wasm-tools component targets` に 2 行を足した）。Modbus ゲストは export しない。コアに SM210–SM211 の 0401 ビット読み、SD210–SD216 の 1401 ワード書き、SM210 ON の 1401 ビット書きだけを組む関数（`drivers/slmp/src/clock.rs`）、ゲストに手順（`slmp-component/src/clock.rs`）と設定 `clock_set`（`disabled` 既定／`enabled`、advanced）を足した。タグとしての SD・SM の書込みは開いていない。実装の PR で決めたこと（作者確認待ち）:

1. 送る前の確かめの順: 設定 `clock_set` → 日付 → 機種 → 宛先。どれかで断るときは何も送らない。設定が `disabled`（未設定を含む）と日付の不正は `rejected`（日付は年 1980–2079、月 1–12、日はその月の日数まで（閏年は 4 で割り切れ、100 で割り切れないか 400 で割り切れる年）、時 0–23、分・秒 0–59。メッセージは不正な項目を名指す）。`clock_set` は `d_u16_write_mode` や許可リストとは独立で、`clock_set` だけがゲストのゲート。
2. 機種: 時計合わせは自分で 0101 を送らず、ハンドシェイクで確定した機種を使う（書込みと同じ）。0101 で `StandardR` と確定した接続だけで進め、G2b のプロセス・SIL2・安全 CPU と MX-R も `StandardR` なので含める（書込みでもこれらを除いていない）。標準 Q は `unsupported`（SM210 が自動で OFF に戻るかを実機で確かめるまで）、Q25PRH/Q12PRH・FX5（4E で使えない FX5 を含む）・型式未知・0101 を断られた接続も `unsupported`。ハンドシェイクが終わっていなければ書込みと同じく `rejected`（"discovery is incomplete"）。
3. 宛先: 自局だけ（ネットワーク 0、局 FFH、I/O 03FFH、マルチドロップ 0）。`network_no` が 0 でない経路と `target_cpu` の `cpu1`〜`cpu4` は、接続先の CPU 自身を指す場合も含めて `unsupported`。4E・3E、TCP・UDP はどれでもよい。監視タイマはその機種群のもの（R は 0010H）。
4. 手順の細部: (1) では SM211 を見ない（前の失敗の ON が残っていても進む）。(4) では SM211 の ON を SM210 より先に見て `device`（code 211）にする。SM210 の読み直しは (4) の 3 回目までで、3 回目も ON なら `verification-failed`。各段の要求の `max-len` は 64。曜日は日付から計算する（0＝日曜、Sakamoto の方法。1980–2079 の全日付で前日の翌曜日になることを試験した）。
5. 終了コード: どの段でも `device`（code は終了コード）で終え、以降は送らない（上の設計どおり）。(3)・(4) の終了コードでは時計が既に変わっている可能性があるので、メッセージにそう書く（F の RMW の確認読みの終了コードは `verification-failed` だが、H は設計どおり `device` にした）。
6. 応答の不正・使い方の誤り: 短い・形の違う応答、4E のシリアル番号や経路の不一致は致命的エラー（`framing`、既存の書込みと同じ）。同じ実行の途中で `time` が変わったら致命的エラー（`protocol`、diagnose-next でタグが変わったときと同じ）。`send` の後に応答なしで呼んだら致命的エラー（`protocol`）。致命的エラーの後と時計合わせの応答待ちの間は、その接続の読取り・書込み・診断・ハンドシェイクも `protocol` で断る（3E では応答を区別できないため。Hub は致命的エラーで接続を閉じる）。逆に、読取り・書込み・診断の応答待ちや、書込み・診断が不確定のままの接続では、時計合わせを `protocol` で断る。`done` の後は応答なしの呼出しで新しい実行を始める。
7. 設定の説明（英語）に、iQ-R の標準 CPU 群・自局だけ、SD210–SD216 と SM210 を書くこと、毎回イベント履歴に 24000 が残るので間隔を短くしすぎないこと、PLC 自身の SNTP・PLC のプログラム・GOT の時刻同期などと上書きし合うこと、Hub のゲートが別に要ることを書いた。アドレスの説明にも、特殊デバイスはタグとしては読取り専用のままで、時計合わせだけが SD210–SD216 と SM210 を書くことを 1 文足した。

試験: コア 3 件（3 つの要求の 4E/3E のバイト列と応答の解読）、ゲスト単体 11 件（日付の検査、曜日、4E/3E の各段のバイト列、SM210/SM211 の各結果、各段の終了コード、応答の不正、他の操作との排他、送る前に断る順、設定）、Wasmtime フィクスチャ 7 件（`slmp-runtime/tests/clock.rs`。小さい world と全部入りの world の両方で bind し、成功、SM210 が残っている、SM211 が ON、SM210 が 3 回 ON、2 回 ON の後に OFF、各段の終了コード、短い応答とシリアル番号の不一致、無効・日付の不正・Q・Q25PRH・FX5・未知機種・他局・マルチ CPU の宛先で送らないこと）を足し、既存の world の互換の試験に新しい 2 つの world を足した。Hub 模擬受入れと実機確認はしていない。残件は下の「H の残件」1–3（STOP 中に合わせられるか、成功時に SM211 が OFF に戻るか、Q の SM210 が自動で OFF に戻るか）のまま開いている。

## CI の拡張順

現在の `changes` は文書、SDK / WIT、Modbus、SLMP、共通・未知パスを分類する。SDK / WIT は両ドライバに波及し、未知パスと共通設定は全領域に倒す。`scaffold` は必須文書と未知ファイルを確認し、`changes` は変更判定テストを実行する。`modbus-test` は Rust 1.85.1 の整形・Clippy・単体テスト・WASM ターゲットの型検査を実行する。`component-build` は WIT と実コンポーネントを検査し、`component-compare` は同じ成果物を Wasmtime で実行して native と照合する。SDK の area ジョブは製品ソースの誤追加を検出し、`slmp-test` は Rust 1.98.1 の整形・Clippy・単体テスト・WASM ターゲット型検査を行う。`ci-gate` は必須ジョブの failure / cancelled / 想定外の skipped を検出する。

SDK に製品コードを導入する際は、その領域の area ガードを実ビルド・テストに置き換える。SLMP の読取りフレームコアには実テストを追加した。現在の Modbus WASM バイナリは `component-build` で一度作り、比較ジョブに artifact として渡す。Rust キャッシュは main で保存し、PR で復元する。PR の古い実行のみキャンセルする。ジョブ・テストの所要時間を記録し、分割数とキャッシュ設定は実測で決める。nextest の分割はまだ行わない。

ソースや依存を増やす変更で追加の承認が必要なら、その時点で止めて状況を報告する。
